# Audit préalable — 22 octobre 2026

Le dashboard est Express/EJS, protégé par requireAdmin et CSRF global. Les conversations, états JSON, scénarios UUID/révisions, payloads bouton/liste et déduplication Meta existent. Les priorités de sécurité précèdent les scénarios ; le simulateur ne crée aucune donnée métier.
La route réelle d’inscription est GET/POST /register (registrationRoutes). Le formulaire étudiant administratif emploie registrationService.createStudentEnrollment, alias de createRegistration : transaction Serializable, disponibilité session/groupe, téléphone/email uniques, niveaux/placement et snapshots de paiement. Aucun modèle ne représente actuellement une demande WhatsApp consentie distincte d’une inscription.
Le catalogue publié vient de publicCourseService ; les sessions ouvertes sont contrôlées par registrationService et enrollmentPolicy. accessLimits autorise cinq essais uniquement pour LEGACY_STAGED ; FULL_PAYMENT donne zéro. Les 60 USD, 16 séances et horaires proposés ne peuvent donc pas être imposés à toutes les formations. Aucune lecture de base de production n’est autorisée ; les écarts réels de prix et horaires restent à examiner dans le catalogue local/Contabo.
Extension prévue : parcours commercial optionnel dans le moteur existant, sans modification des scénarios enregistrés ; collecte temporaire dans l’état de conversation, demande créée uniquement après consentement ; rubrique demandes avec historique et conversion utilisant le corps transactionnel commun d’inscription. Notifications internes et confirmation préparée, sans transport. Contenus éditables avec champs officiels calculés depuis le catalogue. Migration additive, activation locale explicite ; aucun secret ni flag WhatsApp modifié.
